## 1. アプリ概要

### 1.1 dicekey Coffee Stamps とは

dicekey Coffee（架空のコーヒーチェーン、複数店舗運営）が顧客に対して提供するスタンプカード・リワードアプリ。Stellar ネットワーク上で動作する。

| 観点 | 内容 |
|---|---|
| 想定ブランド | dicekey Coffee（架空、複数店舗） |
| デプロイ先 | Stellar Testnet（実証）→ Mainnet（将来） |
| 顧客側体験 | スマートフォンで来店スタンプを貯め、特典を受け取る |
| 店舗側体験 | 店舗スタッフが POS の代わりに発行操作を行う |

### 1.2 採用する Stellar 標準

| SEP | 採用箇所 |
|---|---|
| **SEP-50** v0.1 | 来店スタンプ、特典券、称号バッジ |
| **SEP-41** v0.4 | リワードトークン (dicekey beans) |
| **SEP-45** | Smart Account 認証 |
| **SEP-46** | コントラクトメタデータ |

### 1.3 設計原則

| 原則 | 内容 |
|---|---|
| Stellar 標準準拠 | 既存ウォレットや DEX で表示・取引可能 |
| ノンカストディアル | ユーザーの資産はユーザー自身が完全コントロール |
| Smart Account 中心 | 認証と資産保有を Smart Account に集約 |
| 店舗運営独立 | 各店舗は dicekey 本部の Smart Account のスタッフ Signer として動作 |
| シンプル | 過度な汎用化や抽象化を避ける |

## 2. 4 種のトークンと役割

### 2.1 トークン一覧

| 名称 | 規格 | 譲渡 | 役割 |
|---|---|---|---|
| **来店スタンプ** | SEP-50 NFT (SBT) | 不可 | 1 回の来店記録 |
| **dicekey beans** | SEP-41 FT | 可 | リワードポイント |
| **特典券** | SEP-50 NFT | 可 | ギフト可能なクーポン |
| **称号バッジ** | SEP-50 NFT (SBT) | 不可 | 達成記録（コーヒーマスター等） |

### 2.2 各トークンの詳細

#### 来店スタンプ (Visit Stamps)

- **コントラクト**: `dicekey-visit-stamps`（SEP-50 準拠）
- **発行タイミング**: 顧客が会計時に QR をスキャンしたとき
- **メタデータ**:
  - venue: 店舗識別子（"shibuya", "shinjuku" など）
  - timestamp: 発行時刻
  - issuer: dicekey Coffee の Smart Account
- **譲渡**: 不可（Soulbound）
- **用途**: 累積数で報酬解放、店舗ごとの来店分析

#### dicekey beans

- **コントラクト**: `dicekey-beans-token`（SEP-41 準拠）
- **付与タイミング**: 来店時に自動 mint（1 来店 = 10 beans）
- **decimals**: 0（整数のみ）
- **譲渡**: 可（家族・友人と共有可能）
- **用途**: ドリンク交換、グッズ購入
- **失効**: 最後の獲得から 1 年（SinceLastEarn）

#### 特典券 (Benefit NFTs)

- **コントラクト**: `dicekey-benefits`（SEP-50 準拠）
- **発行タイミング**: Policy 達成時に自動付与、または店舗キャンペーンで配布
- **種類例**:
  - 「無料ドリンク券」
  - 「サイズアップ無料券」
  - 「期間限定 50% 割引券」
- **譲渡**: 可（ギフト用途）
- **失効**: 有効期限あり（メタデータで指定）

#### 称号バッジ (Badges)

- **コントラクト**: `dicekey-badges`（SEP-50 準拠）
- **発行タイミング**: Policy 達成時に自動付与
- **種類例**:
  - 「コーヒーマスター」（来店 100 回達成）
  - 「桜の季節 2026」（春キャンペーン参加）
  - 「朝活マスター」（朝の来店 20 回）
- **譲渡**: 不可（Soulbound、本人性が本質）
- **用途**: アカウント上に永続表示、コミュニティ内での自慢

|---|---|

ただし、本アプリでは以下を **簡略化**:

| 簡略化項目 | 理由 |
|---|---|
| Factory パターン不採用 | 1 つのアプリで完結、デプロイは手動 |
| ProtocolRegistry 不採用 | アプリ単独完結、発見性不要 |
| 複数 issuer 対応不要 | dicekey 1 社で完結 |
| 複数 StampCard 参照不要 | PolicyEngine は本アプリ内のスタンプのみ参照 |
| upgrade 機能 | 初期は不要、後付け可 |
| ページング | 顧客 1 人あたり数百件想定、シンプル実装で OK |

## 4. PolicyEngine の活用（拡張機能）

### 4.1 Policy の例

本アプリで実装する Policy（4 つ）:

| Policy ID | 条件 | 報酬 | 評価モード |
|---|---|---|---|
| `10visit_bonus` | 来店スタンプ 10 個 | 「無料ドリンク券」NFT mint | EventDriven |
| `100visit_master` | 来店スタンプ 100 個 | 「コーヒーマスター」SBT mint | EventDriven |
| `morning_lover` | 朝（6-10 時）の来店 20 個 | 「朝活マスター」SBT mint | EventDriven |
| `spring_campaign` | 期間中（3/1-5/31）の来店 5 個 | 「桜の季節 2026」SBT mint | EventDriven |

すべて **EventDriven**: 来店スタンプが発行された瞬間に PolicyEngine が評価し、条件達成なら自動で報酬を発行。

### 4.2 Policy DSL の使用例

```
10visit_bonus:
  predicate: StampCount { kind: "visit", op: Gte, value: 10 }
  action: IssueStamp { 
    contract: dicekey-benefits, 
    kind: "free_drink_voucher", 
    transferable: true 
  }
  claim_limit: OncePerUser

morning_lover:
  predicate: And [
    Weekday { allowed: [1,2,3,4,5] },
    TimeOfDay { from_hour: 6, to_hour: 10 },
    StampCount { kind: "visit", op: Gte, value: 20 }
  ]
  action: IssueStamp { 
    contract: dicekey-badges, 
    kind: "morning_master", 
    transferable: false 
  }
  claim_limit: OncePerUser
```

### 4.3 PolicyEngine の連携

```
[来店時]
1. 店舗が dicekey-visit-stamps.issue_by_policy で来店スタンプ発行
2. 同時に dicekey-beans-token.mint で 10 beans 付与
3. dicekey-reward-policy.on_event(StampIssued) が呼ばれる
4. 関連 Policy（4 つ）を評価
5. 達成した Policy について、自動で報酬発行
6. 顧客アプリにイベント通知
```

### 5.3 主要フロー

#### フロー A: 朝の来店

```
1. ユーザー: dicekey 渋谷店で会計
2. 店員: POS の「dicekey スタンプ発行」ボタンを押す
3. POS: QR コード表示
4. ユーザー: アプリで QR スキャン
5. ユーザー: パスキー認証
6. システム:
   - dicekey-visit-stamps.issue_by_policy(user, "visit", venue:"shibuya")
   - dicekey-beans-token.mint_by_policy(user, 10)
   - dicekey-reward-policy.on_event(StampIssued, user)
     → Policy 評価 → 該当があれば追加報酬
7. ユーザー: 「+1 スタンプ、+10 beans」通知
```

#### フロー B: 特典券を友人にギフト

```
1. ユーザー A: リワード画面の「贈る」をタップ
2. 受け取り先（B）の Smart Account ID を入力 or QR スキャン
3. 確認画面
4. パスキー認証
5. dicekey-benefits.transfer(A → B, token_id)
6. B 側: 通知「A さんから特典券が届きました」
7. B: 次回 dicekey 利用時に特典券を使う
```

#### フロー C: 特典券を店頭で使う

```
1. ユーザー: 会計時「特典券使います」
2. 店員: POS の「特典券受取」を押す
3. POS: QR 表示
4. ユーザー: アプリで対象の特典券を選んで QR スキャン
5. パスキー認証
6. dicekey-benefits.burn(user, token_id)
7. 店員: POS で割引適用
```

#### フロー D: 100 回達成

```
1. 来店スタンプ発行（普段通り）
2. PolicyEngine が `100visit_master` を評価
3. 達成 → dicekey-badges.issue_by_policy(user, "coffee_master")
4. ユーザーアプリにプッシュ通知:
   「🏆 コーヒーマスターの称号を獲得しました!」
5. アカウントのバッジ一覧に永続表示
```

## 6. 店舗側体験

### 6.1 店舗スタッフのペルソナ

- 店舗で接客する 20-40 代スタッフ
- POS 端末（タブレット）を業務で使う
- 技術的にはレジ操作レベル

### 6.2 認証モデル

dicekey Coffee の Smart Account に、店舗ごとのスタッフ Signer を追加する形:

```
dicekey Coffee Smart Account (admin)
  ├── 本部管理者のパスキー
  ├── 渋谷店スタッフのパスキー
  ├── 新宿店スタッフのパスキー
  └── 京都店スタッフのパスキー
```

スタッフは自分の店舗のタブレットでパスキー認証してログイン。誰のパスキーで発行操作したかが各トランザクションに記録される。

### 6.4 店舗側主要フロー

#### スタンプ発行

```
1. スタッフ:「スタンプ発行」をタップ
2. 画面に QR コードが表示される
   QR の内容: {
     action: "issue_stamp",
     venue: "shibuya",
     timestamp: ...,
     nonce: ...,
     valid_until: now + 60秒
   }
3. 顧客がスキャン → 顧客側のフロー進行
4. スタッフ側: 「✓ 発行完了」表示
```

#### 特典券受取

```
1. スタッフ:「特典券受取」をタップ
2. 注文番号を入力 or QR 生成
3. 顧客が QR スキャン → 特典券選択 → burn
4. スタッフ側: 「✓ 受取完了」表示
5. レジで割引適用
```

#### beans 利用

```
1. スタッフ:「beans 利用」をタップ
2. 交換するドリンク or 額を選択
3. QR 生成
4. 顧客が QR スキャン → 確認 → use_for_benefit
5. スタッフ側: 「✓ 利用完了」表示
6. レジで商品提供
```

## 10. 設計判断のまとめ

| 判断 | 内容 |
|---|---|
| プロトコル抽象を採用しない | アプリとして直接実装 |
| Factory 不採用 | 直接デプロイ |
| ProtocolRegistry 不採用 | アプリ単独完結 |
| 複数 issuer 不要 | dicekey 1 社 |
| スタンプ種別 | 来店のみ（シンプル） |
| beans 付与ルール | 1 来店 = 10 beans（固定） |
| Policy の数 | 4 個（達成 2 + 朝型 1 + 季節 1） |
| 譲渡可能設計 | スタンプ・称号は不可、beans・特典券は可 |
| 認証 | パスキー、Smart Account 経由 |
| 店舗管理 | dicekey Smart Account のスタッフ Signer |
| Sponsored Transactions | やらない（運営は責務を負わない） |
| リカバリ | マルチ Signer 推奨、SEP-30 は将来 |

## 12. リスクと対処

| リスク | 影響 | 対処 |
|---|---|---|
| Soroban API 変更 | 実装手戻り | バージョンピン |
| WebAuthn origin | スタッフが別店舗 PC で使えない | スタッフごとパスキー作成、Smart Account で統合 |
| ガス計算 | 来店時に複数コントラクト呼ぶ → コスト | バッチ化、ガス測定 |
| TTL 切れ | データ消失 | extend_ttl 戦略 |
| 顧客のリテラシー | パスキー登録でつまずく | 初回オンボーディング UX 重視 |
